Interacting with Longleaf

Shell basics, Slurm, and responsible job management

A practical introduction to navigating Longleaf and managing scheduled jobs.

Guiding question: How does a command become a managed job on a compute node?

Essential shell commands

Task Command
Show the current directory pwd
List files ls
Enter a directory cd directory-name
Move up one directory cd ..
Go to your home directory cd ~
Create a directory mkdir directory-name
Print a short file cat filename
Show the last lines of a file tail filename
Page through a long file less filename (press q to quit)
Count the lines in a file wc -l filename
Edit a text file nano filename
Leave Longleaf exit

~ is shorthand for your home directory, so cd ~/example2_single_job works from anywhere. nano is a small editor that runs in the terminal: edit, press Ctrl+O to save, and Ctrl+X to leave. FileZilla’s View/Edit (Module 2) is the alternative for people who prefer an editor on their own computer.

Software modules

Longleaf has many versions of many programs installed, and none of them are available when you log in. Modules turn them on for the current session:

Task Command
See what is available module avail
Search for one program module avail r
Load the default version module add r
Load a specific version module add r/4.4.0
Show what is loaded module list
Unload everything module purge

module avail r lists every R module, with the default marked (D). A loaded module lasts only until you log out, and two rules follow from that:

  • Job scripts load their own modules. A batch job starts with a clean environment, so the script must contain the module add line it needs. UNC recommends a module purge first, so the job does not depend on whatever happened to be loaded when you submitted it.
  • Pin the version when it matters. module add r gives you today’s default, which can change. module add r/4.4.0 gives the same R every time, which is what a project that runs for months needs.

module save stores your current set of modules so they load at every login. Jobs still ignore it, so keep the module add lines in your scripts.

The Slurm job lifecycle

Describe

Write the commands and resource request.

Submit

Send the job script to Slurm.

Monitor

Check whether the job is pending, running, or complete.

Review

Inspect output, errors, and resource use.

Describing a job

A job is described by a short shell script. Lines starting with #SBATCH are directives that tell Slurm what the job needs. Everything after them is what the job runs. This is the script Module 4 submits in Example 2, submit_single.sl, with its comments removed:

submit_single.sl
#!/bin/bash
#SBATCH --job-name=hello_longleaf
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=1
#SBATCH --mem=2g
#SBATCH --time=00:10:00
#SBATCH --output=logs/hello_%j.out
#SBATCH --error=logs/hello_%j.err
#SBATCH --mail-type=END,FAIL
#SBATCH --mail-user=<onyen>@unc.edu

module add r
Rscript --vanilla hello_longleaf.R
Directive Request
--job-name The name shown in the queue
--nodes=1 --ntasks=1 --cpus-per-task=1 One task with one CPU on one node, which is what an ordinary R script needs
--mem=2g Reserve 2 GB of memory
--time=00:10:00 Allow up to ten minutes
--output and --error Files for what the job prints and for its errors; %j becomes the job ID
--mail-type and --mail-user Email when the job ends or fails

The two lines after the directives are the job itself: load R, then run the script. Two details matter more than they look:

  • The job starts in the directory you ran sbatch from. Relative paths such as logs/ and hello_longleaf.R are resolved there, so submit from inside the project folder.
  • Slurm does not create the log directory. If logs/ does not exist, the job fails immediately and leaves no output to explain why. Create it before submitting.

Choosing resource requests

Resource requests affect both whether a job succeeds and when it can start:

  • Too little memory or time: the job may be stopped before it finishes.
  • Too much memory or time: unused resources remain unavailable to other users, and the job may wait longer for a suitable opening.
  • More CPUs: additional CPUs help only when the program is able to use them.

Start with a reasonable estimate plus a modest margin. After a job finishes, use sacct to compare the request with the time and memory the job actually used:

sacct -j <job-id> --format=JobID,State,Elapsed,MaxRSS

Use that information to improve the next request rather than repeatedly reserving the largest possible amount.

Core Slurm actions

sbatch submit_single.sl      # submit; Slurm replies with the job ID
squeue -u "$USER"            # list your pending and running jobs
scancel <job-id>             # cancel one job
sacct -j <job-id>            # state, exit code, and resource use after it finishes

squeue shows one line per job with its state in the ST column:

Code State Meaning
PD Pending Waiting in the queue. The NODELIST(REASON) column says why, such as Priority or Resources.
R Running On a compute node now.
CG Completing Finishing up. It disappears from the list a moment later.

A job that has finished no longer appears in squeue. Use sacct -j <job-id> to see whether it completed, failed, or was killed for exceeding its limits.

Interactive jobs

Not every job is a script. When you want a prompt on a compute node, to test code or install packages before submitting the real thing, ask Slurm for an interactive job:

srun -t 1:00:00 -p interact -n 1 --cpus-per-task=1 --mem=4g --pty /bin/bash

srun takes the same resource flags as the #SBATCH lines, but it waits for the allocation and then opens a shell on the compute node instead of running a script. The prompt changes to show the compute node’s name. When you are done, exit returns you to the login node and releases the resources. Example 1 in Module 4 uses this to run R interactively.

Queue rules and responsible requests

Every job runs in a partition, a group of nodes intended for a particular kind of work:

Partition Used for Maximum run time
general Standard CPU jobs; suitable for most work 11 days
interact Interactive sessions, such as running a graphical program or debugging code 8 hours
datamover Copying large amounts of data between Longleaf file systems, or heavy downloading from the web 11 days
GPU partitions Jobs that use a GPU 11 days unless otherwise noted

general is the default partition. UNC recommends not specifying --partition=general in a job request: leaving it out allows Slurm to place the job on an idle node in another partition.

Partition limits and available hardware can change. Check UNC Research Computing’s current Longleaf documentation when a job has unusual runtime, memory, or GPU requirements.

WarningKeep heavy work off login nodes

Login nodes are shared entry points. Resource-intensive analyses should run through the scheduler on compute nodes.
