How Longleaf Works

Longleaf is made up of many connected computers that are shared by researchers across UNC. Users prepare their work in one place, then ask the cluster to run it using the resources it needs.

From your computer to a compute node

1 · Connect

Connect to Longleaf from a terminal or web browser. You arrive on a login node.

2 · Prepare

Use the login node to organize files, edit code, load software, and describe the resources the work needs.

3 · Schedule

Submit the work as a job. Slurm holds the job in a queue until suitable resources are available.

4 · Compute

A compute node runs the job and writes its output to storage.

Login nodes and compute nodes

A node is one computer within the cluster. Longleaf nodes serve different purposes:

  • A login node is the shared entry point. Use it to work with files, edit scripts, run basic commands, and submit jobs.
  • A compute node supplies the processors and memory that run an analysis.

Users normally do not select or log in directly to a compute node. They request resources through Slurm, which places the work on an appropriate node.

WarningKeep demanding work off the login node

Many people share each login node. Running an analysis there can slow the system for everyone. Submit computational work through Slurm so that it runs on a compute node.

What is Slurm?

A job is a request to run a program using specified cluster resources. Longleaf uses Slurm, a workload manager and job scheduler, to coordinate those requests.

Users do not normally select a compute node and start an analysis directly. Instead, they tell Slurm what program to run and what resources it needs. Slurm then manages the job from submission through completion.

Why Longleaf needs a scheduler

Longleaf has many users, many jobs, and a limited supply of compute nodes with different amounts of memory and different kinds of hardware. Slurm provides an orderly way to share those resources.

Slurm:

  • keeps track of available cluster resources;
  • holds waiting jobs in a queue;
  • matches jobs with appropriate compute resources;
  • starts and monitors work on the assigned resources; and
  • releases the resources when a job finishes.

This prevents users from competing directly for compute nodes and keeps one job from using resources that Slurm has assigned to another.

What happens after submission?

  1. Slurm checks the job request and assigns it a unique job ID.
  2. The job enters the queue, usually with a pending status.
  3. Slurm waits until suitable CPUs, memory, and any specialized hardware are available.
  4. Slurm allocates those resources and starts the job on a compute node.
  5. The job finishes or stops, Slurm records its status, and the resources become available again.

A pending job has not necessarily encountered a problem. It may be waiting because the requested resources are currently in use, no available node has enough memory, the job needs specialized hardware, or other jobs currently have higher priority.

What Slurm does not do

Slurm manages resources and jobs, but it does not rewrite or optimize the program being submitted. In particular:

  • requesting more CPUs does not make single-threaded code use them;
  • requesting more memory does not make code run faster; and
  • Slurm does not automatically know how much time or memory a program will need.

Users therefore need to make reasonable initial requests and refine them using information from completed jobs. Module 3 shows how to submit and monitor jobs and review their resource use.

What does a job request?

For most jobs, the essential requests are:

Resource What it means
CPUs The processor capacity available to the job
Memory The short-term working space, or RAM, available while the program runs
Time The maximum amount of time the job is allowed to run
Partition Which group of nodes the job may use. Most jobs leave this unset; interactive sessions use interact

Asking for more resources does not automatically make a program run faster. A program must be written to use multiple CPUs, and unused memory does not improve its speed. Requests that are close to what the job actually needs also make it easier for Slurm to find a place for the job to run.

Memory and storage

Memory and storage serve different purposes:

  • Memory holds the data and instructions a program is actively using. It is temporary and belongs to the compute node running the job.
  • Storage holds scripts, datasets, logs, and results as files. Files remain available after a job ends.

One useful comparison is a desk and a filing cabinet. Memory is the desk where current work is spread out. Storage is the filing cabinet where materials are kept between tasks. A larger desk lets you work with more material at once, but it does not necessarily make the work faster.

Key terms

Term Meaning
Login node The shared entry computer used to prepare and submit work
Compute node A computer where scheduled work runs
Slurm The system that queues jobs and assigns resources
Job A unit of work submitted to Slurm
Partition A logical group of compute nodes
Software module A way to make installed software available

Summary

You use a login node to prepare and submit work. Slurm finds appropriate resources, a compute node runs the job, and the results are written to storage.

Later modules show how to connect to Longleaf, submit a job, and choose appropriate resource requests.
